1. Goals and boundaries

Pharos reduces the effort needed to turn a brief reported disaster situation into a reviewable responder case. It preserves reported urgency while separately handling content concerns, makes evolving facts auditable, and prevents an unverified assignment or invented ETA from becoming reassurance to a caller.

Residents use a phone. Beacon is responder-facing. Current integrations are Photon, LiveKit, a Cloudflare Worker with SQLite Durable Objects, and the Beacon web client. This is a hackathon prototype with shared-role authentication and configured demonstration areas/responders.

Non-goals for this release: real-world truth verification, automatic dispatch, medical diagnosis, GPS/flood sensing, individual professional identity verification, resident warning notifications, SMS campaigns, and two-party call relay. No MongoDB Atlas, Tiger Data, Gemini API, Solana, or Vultr integration is claimed.

  |              |                    |<-- claim + explicit desk progress ------|
  |              |-- private poll --->|                      |                 |
  |<-- current server-authored update -|                      |                 |

  |              |                    |<-- manual private playback -------------|

Consented partial turns can create or update a case before hangup. Review uses cumulative caller context but never assistant dialogue, phone numbers, or raw audio. The Worker validates the assessment against the current source call/sequence and exact caller quotations. During an active intake, progress polling returns only the minimal current desk-authored message; speech waits for a quiet gap.

At end, phone legs are removed before slower finalization and recording upload. Cleanup and upload share a bounded shutdown deadline. Missing final assessment becomes unavailable/human review rather than a fabricated clear result.

Relations: a case may have multiple conservatively linked calls and history snapshots; each decision points to exact review evidence; each retained recording belongs to its source call. One revoked/expired historical source cannot erase newer valid facts or restore an older snapshot.

5. Review, urgency, and response state

Human acceptance/dismissal requires a meaningful reason and expected review version, source call, and sequence. Dismissal keeps the report and history and does not silently cancel an existing owner. A follow-up owner can work on verification while response is held.

Urgency suggestions use reported life-safety danger first, then time-sensitive support, urgent shelter/evacuation/supply needs, then follow-up. New life-safety evidence can override a prior human downgrade. Normal response additionally requires approved service coverage, capability, availability, and capacity.

Response states are explicitly desk-reported: On the way, Delayed, Arrived, or Unable. Travel/delay requires a fresh 1–180 minute estimate. Changed facts/location/coverage/review can invalidate prior progress. Reaccepting a report never automatically restores an old ETA.

6. Contextual review design

The live contextual reviewer is distinct from the synthetic rule-inspection workbench. It checks for supported pressure toward a concrete unsafe action, or the separate narrow combination of explicit current fabrication admission plus resource-diversion request. Exact caller-only quotation validates evidence; ordinary emotion, urgency, accent, corrections, missing names, and quoted victim reports cannot establish fraud.

ControlImplemented bound
Input isolationConsented caller text only; excludes assistant turns, contacts, raw audio and tone.
ConcurrencyOne in-flight request; newest snapshots coalesce.
BudgetAt most eight requests per call; serialized input/schema ≤15KB; output ≤800 tokens.
Failure behavior8-second timeout, no tools, no retries; unavailable/invalid/uncertain means human review.
ValidationStrict known categories, strict uncertain boolean, exact evidence spans and current source sequence.
StalenessLate/canceled/revoked work cannot revive evidence or overwrite current human decision.

A no-concern result is not identity/truth verification. The prototype has no validated field accuracy or probability of deception.

7. Callback reconciliation and concurrency

Repeat linkage requires fresh consent, explicit same-situation intent, independently supplied substantial matching location, one eligible recent open case, and an ended previous report. Shared-phone ambiguity, active parallel calls, broad areas, closed/dismissed cases, or expired/revoked sources prevent silent merging. Generic location references preserve earlier specific landmarks; explicit corrections remain auditable.

Version/call/sequence checks reject stale human actions and model results. Identical ingestion/audio retries are idempotent; conflicting retries cannot mutate the accepted payload or extend retention. Human work on a provisional case prevents deleting it during later matching. The Durable Object centralizes state transitions in its SQLite-backed authority; this is not a claim of global multi-region failover or a benchmarked scale target.

8. Security, consent, and retention

The browser authenticates with signed shared-role sessions. HTTPS cookies are HttpOnly, SameSite=Strict, Secure, with an eight-hour lifetime. Coordinator approval is role-restricted; service-area filtering is a view, not authorization. Ingestion and progress/audio upload require the separate bearer credential; ingest authorization does not permit responder recording playback. URL tokens never authorize audio.

Contacts use encrypted storage and purpose-separated keyed lookup. Audio uses AES-GCM with purpose/call/sequence binding in existing SQLite storage. Capture starts after explicit acknowledged audio consent and only includes the selected caller’s remote track. It uses memory rather than local recording files or a new recording service.

Recording propertyContract
Format16kHz mono PCM16; at most 180 seconds / 5,760,000 bytes.

Provider retention and already received browser memory have separate limits; Pharos does not promise deletion of external provider copies. Shared passwords and no verified individual identities remain material prototype limitations.

10. Deployment and operational evidence

Maintained web sources live in Product/. sync-site.mjs copies supported public assets and writes a credential-free build stamp. Vite invokes synchronization on direct DeepSpace deployments too. Release work pauses the backend watcher until it is inactive, checks types/build/tests, commits and pushes source, publishes using the existing application, and verifies the served source stamp and access boundaries.

Public build.json identifies commit, dirty flag, build time, and canonical repository. Platform release metadata lacks GitHub commit lineage, so source stamps and pushed clean source provide traceability. Generated local-secret build files must be removed from bundles.

This documentation release reran all 243 JavaScript backend/domain/UI checks successfully. The separately recorded offline voice lane reports 108 passing tests on its prior fingerprint. One prior real Photon intake and one later hosted synthetic WebRTC pass are separate evidence. Current-build phone, callback, concern/audio playback, and visual acceptance are not implied by those results. See the complete test specification.

Known operational limits: one demonstration incident/desk, provider dependencies, configured service areas and responders, no measured availability/throughput/recovery guarantee, bounded call/reviewer budgets, and shared-role access. Future work includes stronger identity/auditing, operational validation, and separately consented resident warning features.
